# Lathe — 10 · 模糊任务 PRD 模板与填写规范

> 2026-09-23 · 状态：待评审
> 前置：[02-design.md](./02-design.md)（状态机、验证设计）、[07-prd-orchestration.md](./07-prd-orchestration.md)（编排图约束）
> 本文是**规划智能体产出物的结构契约**：模糊任务经多轮对话后形成的 PRD 长什么样、
> 每一节怎么填、什么条件下算定稿、定稿后怎么变成正式任务与编排图。

---

## 0. 背景与决策

### 0.1 体系转向

Lathe 从「只接 Linear 下料的执行器」转为**自有任务平台**：任务在 Lathe 内新建，
Linear 降为可选的外部 tracker 扩展（同步进、回写出，但不再是任务存在的前提）。

任务按**成熟度**分两类：

| | 正式任务 | 模糊任务 |
|---|---|---|
| 输入 | 已写清的需求或缺陷 | 一句话、一个想法、一段模糊描述 |
| 进入 | 执行管线：分诊 → 实现 → 红-绿验证 → PR | **规划管线**：多轮对话 + 读代码 → PRD |
| 产出 | PR | 一份本文定义的 PRD |
| 之后 | — | 人批准 PRD → 一键生成正式任务 + 编排图 → 各自进执行管线 |

### 0.2 本轮拍板的决策

| # | 决策 | 理由 | 代价 |
|---|---|---|---|
| D10-1 | **推翻 07 §1.4 非目标「AI 自动拆解成图」**：PRD 由智能体直接给出任务拆分与依赖，人确认后一键生成编排图 | 拆分是 PRD 的自然产物，人手工照着 PRD 建任务是重复劳动 | 拆分质量成为新的风险面，由 §4 结构约束 + §7 自检兜底 |
| D10-2 | **产品边界重述**：「不做需求澄清、不猜」仍成立，但含义收窄为「**执行阶段**不猜」。规划阶段智能体可以帮人把需求想清楚，产物是**必须人签字的 PRD**，不是直接猜着写代码 | 30~50% 「单子没写清」的需求从被打回变成被平台写清，这是模糊任务存在的意义 | 边界从一条硬规则变成两条（规划可想 / 执行不猜），需要在 README 边界段同步改写 |
| D10-3 | 由 PRD 生成的正式任务**依旧过分诊** | 不能因为是自己生成的就免检；分诊同时是 PRD 质量的回归探针（分诊打回率高 = 模板或智能体有问题） | 每个任务多一次便宜通道的调用 |
| D10-4 | PRD `approved` 后**不可变**。漏了开新 PRD，新 PRD 可引用旧 PRD 作为上下文 | 增量修订要 diff 任务集、处理已在跑的任务，复杂度不值 | 小遗漏也要走一份新 PRD（可以很短） |
| D10-5 | 单任务量级默认 **≤ 400 行净改动 / ≤ 8 个文件 / 一组红-绿测试**，仓库级可配置 | 见 §4.2 | 估算由智能体读代码给出，会有误差；估错最坏是一个偏大的 PR |
| D10-6 | **对抗复核必跑**（§5.5），不按 PRD 类型跳过 | 它是 AC 唯一的「红阶段」 | 每份 PRD 多一次只读 agent 调用 |
| D10-7 | 对话形态为**多轮交互式**，每轮 ≤ 3 个问题，每轮交付完整 PRD 快照 | 一次跑完的 PRD 只能把不确定处列成问题清单，对齐意图的主要手段（§5.4 例子法）需要来回 | 需要会话状态与 UI，规划管线不是 headless 一跑到底 |
| D10-8 | 规划智能体**可只读访问目标仓库** | §2 问题陈述与 §5 现状分析必须带 `file:line` 证据；不读代码的 PRD 是空谈 | token 与一份只读 worktree 的成本；复用预览环境「AI 推荐」的 plan 权限只读模式 |

### 0.3 三条约束决定模板形状

1. **PRD 的读者首先是分诊器和验证管线，其次才是人。** 每个拆出的任务要能过「明确度判定」，
   且要能让实现 agent 写出先红后绿的测试。因此验收标准与任务描述不能是散文。
2. **编排图有硬约束**（07 §F1.2、§F3.3）：单仓库；`depends_on` 单值 ⇒ 入度 ≤ 1（允许一个
   前驱有多个后继，图是森林）；链长默认上限 4（超了警告不禁止）；任务类型 ∈ `fix|feature|hotfix`。
   任务拆分那一节必须结构化，让「一键生成」是确定性操作，不再经过一次 LLM 解释
   ——与 `.lathe/repro.json`「声明优先于猜测」同一哲学。
3. **多轮对话的产物要沉淀。** 每节带状态标记，另有独立的决策记录，后续轮次不许重问已拍板的问题。

## 1. PRD 生命周期

### 1.1 状态

```
drafting ──► awaiting_answers ──► drafting ...（循环若干轮）
   │
   └──► ready_for_review ──► approved ──► converted
              │                 
              └──► drafting（人打回）
任意非终态 ──► abandoned
```

| 状态 | 含义 | 谁推动 |
|---|---|---|
| `drafting` | 智能体在填写/修订 | 智能体 |
| `awaiting_answers` | 本轮问题已提出，等人回答 | 人 |
| `ready_for_review` | 自检清单（§7）全过、对抗复核（§5.5）完成，等人批准 | 人 |
| `approved` | 人已签字，PRD 冻结 | 系统 |
| `converted` | 已生成正式任务与编排图（终态） | 系统 |
| `abandoned` | 人放弃（终态） | 人 |

### 1.2 节状态标记

每一节标题后带一个标记：

- **✅ 已确认** —— 人明确拍过板
- **🤖 推断** —— 智能体从代码或对话推出，待人过目
- **❓ 待答** —— 挂着未决问题（Q-n）

**进入 `ready_for_review` 的条件：没有 ❓；所有 🤖 至少被人看过一遍变成 ✅。**
「看过一遍」在 UI 上是逐节的确认动作，不是整页一个按钮。

### 1.3 对话协议

| 阶段 | 智能体做什么 | 主要产出 |
|---|---|---|
| A 理解 | 复述意图、判定 PRD 类型（缺陷/功能/重构）、提 ≤ 3 个关键问题；**先不读代码** | §0 §1 草稿 |
| B 探索 | 只读方式进仓库；出现状分析与问题陈述证据；方案有分叉时**列选项让人选** | §2 §5 §6 |
| C 收敛 | 定目标/非目标/场景；按 §5 七层防线写验收标准；用例子与反例逐条对齐 | §3 §4 §7 |
| D 拆分 | 出任务表 + 依赖 + 覆盖矩阵；人可调整依赖、合并/拆分任务 | §8 |
| E 定稿 | 跑对抗复核、跑自检清单、列出剩余 ❓；人批准 | §9 §10 附录 |

三条纪律：

1. **每轮最多 3 个问题。** 问题轰炸的结果是人不答。问题要按「答案会改变什么」排序，
   不影响方案走向的问题不问，智能体自己 🤖 推断后让人过目。
2. **每轮交付完整 PRD 快照**，不是只交问题。人随时能看全貌。
3. **不重问 §10 已有记录的问题。** 人改主意可以，但要走「修改决策」而非「被重新问到」。

## 2. 模板正文

各节的「目的 / 填写规则 / 变体差异」。示例片段用本仓可能出现的需求写，只作格式示意。

### §0 元信息

| 字段 | 说明 |
|---|---|
| PRD 编号 | 系统生成，如 `PRD-42` |
| 来源模糊任务 | 任务 ID 与原始输入原文（**原文不可编辑**，它是所有推断的根） |
| 目标仓库 | 唯一。跨仓库不在 v1 范围 |
| PRD 类型 | `defect`（缺陷）/ `feature`（功能）/ `refactor`（重构），决定 §4 §7 变体 |
| 引用 PRD | 可选，接续某份已 `converted`/`abandoned` 的 PRD |
| 轮次 / 状态 | 当前对话轮次；§1.1 状态 |

### §1 一句话

**目的**：说清「做什么、给谁、解决什么」。
**规则**：≤ 60 字。写不进一句话说明还没想清楚，智能体应回到提问而不是硬写。

> 示例：让管理员在系统设置里配置任务预览的资源阈值，避免预览把宿主机打满。

### §2 问题陈述（Why）

**目的**：证明问题真实存在。
**规则**：三列表「现状 | 证据 | 后果」。证据**必须可查**：代码位置 `file:line`、现有行为的
复现步骤、日志、数据。禁止「感觉应该做」。缺陷类 PRD 这一节的证据必须包含一次复现。

| 现状 | 证据 | 后果 |
|---|---|---|
| 预览阈值写死 90% | `internal/preview/gate.go:31` 常量 | 大内存机器上预览被无谓拒绝 |

### §3 目标与非目标

**目标**：编号 G-n，每条附「怎么知道达成了」。
**非目标**：明确不做 + 理由。**这一节是防扩 scope 的主闸门**：对话里人每提一个新想法，
智能体必须把它归入目标或非目标，不许悬空。

### §4 用户场景

**规则**：S1 主场景、S2…，每个用 Given / When / Then 写成一条可走的路径。
**缺陷类变体**：本节改为「复现路径」——前置条件、步骤、期望 vs 实际。它将直接成为红阶段
复现测试的蓝本。
**重构类变体**：本节改为「行为清单」——列出重构范围内**必须保持不变**的对外行为，
每条指向一个现有测试或标注「无测试覆盖，需先补特征测试」。

### §5 现状分析（代码侧）

**目的**：让人判断智能体到底看懂了没。
**规则**：涉及模块与入口、现有约束（唯一索引、状态机边、接口契约、配置消费方）、
可复用的现成机制、改动会波及的地方。全部带 `file:line`。同时列出**该区域现有测试**，
它们是 §7「不变量保持」类 AC 的来源。

### §6 方案

- **核心决策**：结论先行 → 理由 → 代价（本仓 docs 写法）。
- **备选与为何不选**。
- **变更清单**：数据模型 / 接口 / 状态机 / 配置项。**新增配置项必须写消费方**（AGENTS.md §1 铁律 3）。
- 方案有分叉时，智能体**列选项让人选**，不替人选。选择结果进 §10。

### §7 验收标准

分两块，**两块都必须有**：

**§7.1 AC 表** —— 本 PRD 特有的行为。不是自由列表，是有固定行的表（§5.2），每行要么填
AC，要么写 `N/A + 理由`。每条 AC：

| 字段 | 规则 |
|---|---|
| 编号 | `AC-n` |
| 类别 | §5.2 的七类之一 |
| 陈述 | Given / When / Then，带具体值 |
| 判据 | 观察什么：HTTP 状态 / 表行 / 事件 / UI 元素 / 度量值 |
| 验证方式 | `自动测试` / `脚本` / `人工走查`（三选一，人工走查须写清步骤） |
| 追溯 | 回指的 G-n 与 S-n |
| 交付任务 | §8 中的 T-key |

**§7.2 例子与反例** —— 每条 AC 附 1~2 个正例、1 个反例，以及一条「反向确认」
（按此 AC，X 情况不会被拦，是否接受）。人对例子的判定记入 §10。

**§7.3 上线条件（Definition of Done）** —— **由系统附加，智能体不编写**：

- §7.1 全部 AC 通过
- 受影响模块回归绿、lint 绿
- 含迁移的任务：迁移可 `down`
- 新增配置项有消费方并登记 README
- 行为变更同步文档
- UI 变更：经预览环境人工走查，走查步骤在对应 AC 里
- 凭据/令牌不出现在日志、事件流、agent 子进程 env

**重构类变体**：§7.1 只允许两类 AC——「行为保持」（现有测试全绿；未覆盖的行为先补特征
测试，且特征测试要先证明能在旧代码上绿、被破坏时能红）与「结构度量」（依赖方向、
文件/函数数、重复代码量等，目标值写死）。

### §8 任务拆分与依赖

**规则**：Markdown 表格给人看，同时附 §4 定义的结构化块给「一键生成」用。两者由同一份
数据渲染，不允许不一致。每个任务必须能**单独拿出来通过分诊**。

### §9 风险与未决

- **风险**：影响 / 概率 / 缓解。
- **未决问题**：`Q-n`，「问题 | 谁答 | 状态」。定稿前必须清零——要么答了，要么人显式
  标「接受不答」并进 §10。

### §10 决策记录

对话里每次人拍板一条：轮次、问题、决定、理由。条目类型：

- `选项选择`（§6 方案分叉）
- `边界确认`（§7.2 反向确认的结果）
- `例子判定`（§7.2 正例/反例的判定）
- `接受未决`（§9 显式接受）
- `修改决策`（推翻早前条目，指向被推翻的编号）

### 附录

- **A 对话摘要**：每轮 2~3 行
- **B 代码证据索引**：全部 `file:line` 引用去重汇总
- **C 对抗复核报告**：§5.5 的原样输出与处置结果
- **D 术语**

## 3. 变体差异速查

| 节 | 缺陷 `defect` | 功能 `feature` | 重构 `refactor` |
|---|---|---|---|
| §2 证据 | **必须含一次复现** | 代码/行为证据 | 结构问题证据（度量值） |
| §4 | 复现路径 | 用户场景 | 行为保持清单 |
| §7.1 | 复现修复 AC 为必填 | 七类完整表 | 仅「行为保持」+「结构度量」 |
| §8 首节点 | 复现测试可与修复同任务 | 常为迁移或接口任务 | **必须是「补特征测试」任务** |
| 对抗复核 | 跑 | 跑 | 跑 |

## 4. 任务拆分的结构化契约

### 4.1 格式

```json
{
  "version": 1,
  "repo": "owner/repo",
  "tasks": [
    {
      "key": "T1",
      "title": "预览资源阈值改为系统设置项",
      "kind": "feature",
      "depends_on": null,
      "description": "把 internal/preview/gate.go 的 90% 常量改为读 system_settings.preview_threshold_pct；非法值（<1 或 >100）启动拒绝。必须交付：新增测试证明阈值可配且非法值被拒（在旧代码上该测试应失败）。",
      "files_hint": ["internal/preview/gate.go", "internal/store/settings.go"],
      "acceptance": ["AC-1", "AC-2", "AC-5"],
      "verify_hint": "heavy",
      "estimate": { "lines": 120, "files": 3 }
    }
  ]
}
```

| 字段 | 约束 |
|---|---|
| `key` | PRD 内唯一 |
| `kind` | `fix` / `feature` / `hotfix`（与 `tasks.task_kind` 一致） |
| `depends_on` | `null` 或一个已存在的 `key`；**入度 ≤ 1**；无环；链长超仓库上限（默认 4）时警告 |
| `description` | 写到能过分诊：目标、涉及范围、**必须交付的复现/验收测试是什么** |
| `files_hint` | **参考**，不约束实现 agent；生成任务时以「参考文件」段落进正文 |
| `acceptance` | 非空；引用的 AC 必须存在 |
| `verify_hint` | `light` / `heavy`，仅供人看工作量；真实定档仍在 diff 后（02 §5.1） |
| `estimate` | 智能体读代码后的估算，用于 §4.2 自检 |

### 4.2 单任务量级（D10-5）

**规则：一个任务 = 一个可独立验证的行为变化 = 一个 PR。**

| 维度 | 上限信号（超过就拆） | 下限信号（低于就合） |
|---|---|---|
| 验证 | 需要超过一组独立的红-绿测试 | 没有任何一条 AC 能由它单独交付 |
| 范围 | 因**不同理由**跨越多个模块/包边界 | 只是另一个任务的机械前置（空表、空接口） |
| 体量 | 预估净改动 > `prd_task_max_lines`（默认 400）或 > `prd_task_max_files`（默认 8） | — |
| 定档 | 混合「纯前端展示」与「后端/迁移」两类改动 | — |

例外：**数据库迁移单独成任务**，哪怕只有十几行（`sql-migration` 要求一次迁移一件事，
且它是链上最常见的前驱）。

**能并行就不要串链**：只有 B 真的要用 A 的代码才连线。每多一个链节点就多一份 worktree、
一轮验证、一次前驱合并后的 rebase 跟进。

为什么是这四条（都来自本系统自身机制，不是通用经验）：

1. 红-绿判决按任务下。一个任务揉两个行为 ⇒ 两组复现测试，一组红立不起来整个任务转
   `blocked_spec`，好的一半跟着卡死。
2. 修复回路有限次。diff 越大，agent 越容易在不相关区域来回改，把次数烧光。
3. 定档按 diff 改动面。前后端混合必升 heavy；拆开后前端走 light，双通道（默认 2/1）才用得上。
4. 合并是人点的，PR 可读性就是吞吐上限（00 §2.1）。400 行 / 8 文件是 review 质量陡降的经验阈值。

**配置项与消费方**（铁律 3）：`repos.prd_task_max_lines`（默认 400）、`repos.prd_task_max_files`
（默认 8），消费方是规划智能体的 §7 自检（超限拒绝进 `ready_for_review`，除非人在 §10
记录「接受超限」）。仓库配置页可改；非法值（≤ 0）保存拒绝。

### 4.3 一键生成的语义

`approved` 后，人点「生成」：

1. 校验结构块（§4.1 约束）——失败即拒绝，不修正。
2. 每个任务建一条正式任务：正文 = `description` + 「验收标准」（引用的 AC 全文）+
   「参考文件」（`files_hint`）+ 「来源 PRD」链接；`task_kind = kind`。
3. 依赖 `depends_on` 落成一张编排图（`flows` + `tasks.depends_on`），根节点并行，
   `depends_on_at` 取默认 `pr_open`。
4. 每个任务进 `queued`，**照常过分诊**（D10-3）。分诊打回的任务在 PRD 页可见，作为
   PRD 质量信号（§5.7）。
5. PRD 转 `converted`；任务与 PRD 双向可导航。

## 5. 验收标准的七层防线

**前提要诚实：没有模板能「保证」AC 等于真实意图。** AC 是意图的模型，模型与意图之间的
缝正是要人签字的原因。下面七层做的是把缝压窄、照亮、并在出问题后收窄。每层拦一类典型失效。

### 5.1 可追溯闭环 —— 拦「漏了目标」与「测了没人要的东西」

每条 AC 回指一个 G-n 和一个 S-n；每个 G、每个 S 至少一条 AC；每条 AC 至少一个 T 交付。
四张表两两做覆盖矩阵，**任何方向出现孤儿都是缺陷**，自检不过。

### 5.2 类别强制填空 —— 拦「只写了正向路径」

AC 表有固定行，每行要么填 AC，要么写 `N/A + 理由`，不许留空：

| 类别 | 本系统里的典型例子 |
|---|---|
| 正向路径 | 功能按场景走通 |
| 失败路径 | 非法输入拒绝；非属主访问返 404 不返 403 |
| 边界与幂等 | 空集合、上限、并发；webhook 重投递不重复建任务 |
| 不变量保持 | 「验证体系不可削弱」——改动后任何路径到 `pr_open` 仍必经 `verifying` |
| 非功能 | 超时上限、凭据不进日志/事件流、迁移可 down |
| 可观测性 | 状态转移落 `task_events`，失败有 `failure_stage` |
| 兼容与默认 | 新功能对存量部署默认关闭（先例：标签接单默认空串） |

`N/A + 理由` 逼智能体对每个维度想过再说不需要——「配置了但没接线」教训的同一逻辑：
显式优于沉默。

### 5.3 AC 必须可执行 —— 拦「形容词冒充标准」

Given / When / Then + 具体值 + 判据。**禁用词表**：正确、合理、友好、快速、稳定、完善、
优雅、健壮——出现即打回，除非旁边有数字或判据。检验法：「这条 AC 我现在能写出断言吗？」
写不出来的不是 AC，是愿望。

### 5.4 用例子对齐意图 —— 拦「看懂了字面，没看懂含义」

人不擅长审抽象标准，擅长判断具体案例。每条 AC：

- 给 1~2 个正例 + 1 个反例，问「这个情形算不算通过」——反例暴露 AC 的边界在哪。
- **反向确认**：「按这份 AC，X 情况**不会**被拦住，你接受吗？」隐含期望几乎全藏在这里。

判定结果进 §10（`例子判定` / `边界确认`）。这是对话里最该花时间的地方。

### 5.5 对抗复核 —— AC 自己的「红阶段」

红-绿的逻辑：一个不能先失败的测试无权声称验证了什么。同理：**一组任何实现都能过的 AC，
无权声称覆盖了意图。**

进入 `ready_for_review` 前，起一个**独立上下文**的只读 agent（不看 §5 §6，只看 §1–§4 与 §7），
任务：

1. **构造一个能通过全部 AC 却违背意图的实现**（恶意合规）。#492「只写测试没实现」是真实
   案例。构造得出来 ⇒ AC 有洞 ⇒ 转 ❓。
2. 列出 §4 场景里 AC 未覆盖的分支。

报告原样进附录 C，处置结果逐条标注。人审 PRD 时能看到「有人试过攻它、攻不动」。

### 5.6 上线条件与 AC 分开 —— 拦「过了 AC 就等于能上」

AC 只覆盖本 PRD 引入的行为；上线还要满足平台级不变量。§7.3 由系统附加，不由智能体编写。
把 DoD 显式列出，「过了验收就能上」这句话才成立——因为定义里把该有的都放进去了，而不是
让 AC 独自背全部责任。

### 5.7 验收逃逸回流 —— 跨 PRD 的长期机制

任务上线后，若 PR review 提了 AC 未覆盖的问题、后来回了 bug、或分诊打回了 PRD 生成的任务，
记一条「AC 漏项」挂回原 PRD，标注属于 §5.2 哪个类别。两个用途：§5.2 类别表按证据长
（与 AGENTS.md §9 事故清单同一方法论）；计算**验收逃逸率**——评价规划智能体好坏唯一说得清的指标。

## 6. 定稿自检清单

进入 `ready_for_review` 前必须全过。分三档：机器可判 / 智能体自判 / 人判。

### 6.1 机器可判（结构校验，失败即拒绝）

- [ ] 无 ❓ 标记的节
- [ ] §1 ≤ 60 字
- [ ] §7.1 七类每行非空（AC 或 `N/A + 理由`）
- [ ] 每条 AC 有判据、验证方式、追溯 G/S、交付 T
- [ ] 覆盖矩阵无孤儿：G↔AC、S↔AC、AC↔T 三对双向
- [ ] §7 陈述不含禁用词（无判据伴随时）
- [ ] §8 结构块合法：key 唯一、`depends_on` 有效、无环、入度 ≤ 1、`acceptance` 非空且存在
- [ ] 每个 T 的 `estimate` 不超仓库上限，或 §10 有 `接受超限` 记录指向该 T
- [ ] 链长 ≤ 仓库上限，或有警告确认记录
- [ ] 附录 C 存在且每条发现有处置标注
- [ ] 重构类：§8 首节点 kind 与标题标识为特征测试任务

### 6.2 智能体自判（写进附录 A 最后一轮）

- [ ] 每个 T 的 `description` 单独拿出来，我会判它「明确、可动手」吗？
- [ ] §3 非目标里有没有对话中人提过、但我没归位的想法？
- [ ] §5 引用的每个 `file:line` 现在还成立吗（读代码是几轮前的事）？
- [ ] §6 每个新增配置项写了消费方吗？

### 6.3 人判（UI 逐节确认）

- [ ] 所有 🤖 已过目转 ✅
- [ ] §7.2 每条反向确认都有明确的接受/不接受
- [ ] 附录 C 的处置我认可

## 7. 导出

- **Markdown**：完整 PRD 渲染为独立 `.md`，节标记以文本形式保留（`[已确认]` 等），
  可回写进目标仓库 `docs/`（由人决定是否提交，Lathe 不自动 push）。
- **JSON**：结构化全量（每节一个字段 + §8 数组 + §10 数组 + 附录），供外部工具或下一份
  PRD 引用。
- 两种导出在任何状态下都可用；`approved` 之后导出内容冻结。
