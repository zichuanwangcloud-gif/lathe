## 2. D2 的后果：准入策略下沉为用户设置项

label 触发方案里，"人愿不愿意打这个 label"本身是一次免费的人工分诊。改成「指派给我即自动接单」后这个闸门消失了。

**但闸门该不该存在，取决于该用户 workspace 的单子质量，不该由平台统一决定。**（早期版本本文档在此处主张强制 Plan-first 观察期，已否决 —— 那是把单一风险偏好硬编码进所有人的流程。）

### 关键修正：分界线是"明确度"，不是"任务类型"

不可自动化的单子，特征不是"它是产品讨论"，而是**没写清楚**。一个内容为"登录有问题"的 bug 单和一个需求未定的单，对 agent 是同一类障碍。因此档位按**单子明确度**切分。

### 设计：准入模式（个人设置，按用户/按仓库可覆盖）

| 模式 | 行为 | 适用 |
|---|---|---|
| `direct` 直接干 | 接单即实现，不分诊不询问 | 单子质量稳定、清一色 bug + 需求开发的用户（**本账户默认取此档**） |
| `guarded` 兜底询问 | 默认直接干；仅当分诊置信度低于阈值时回帖提问并暂停 | 绝大多数场景的推荐默认值 —— 95% 的单等于 `direct`，剩下 5% 免费兜底 |
| `plan-first` 计划先行 | 先只输出实施计划回帖，静默观察期（默认 10 min）无异议后自动执行 | 单子质量参差的团队，或新接入的仓库试水期 |
| `manual` 逐单确认 | 每单都需人工点确认才动手 | 新用户 / 高危仓库 |

阈值、观察期时长均可配置。**新用户出厂默认 `guarded`** —— 因为平台此时不知道该 workspace 的单子质量；用户确认自己的单够清楚后自行切到 `direct`。

### 待验证的经验假设

「30~50% 的单不适合自动化」是推测，非实测。**应在 Phase 0 用真实 Linear 数据校准**：抽样最近 N 个已指派 issue，统计其中含明确复现步骤/验收标准的比例。若实测明确率 >85%，则 `direct` 应升为出厂默认，本节的兜底设计相应降级。

## 3. D3 的后果：这是分布式系统，不是单机脚本

多节点定位带来的硬性要求：

- **任务必须能在任意节点从零重建环境**。不能假设 `/opt/CloudRouter` 存在。每个节点需要：仓库 bare mirror 缓存 + 共享 pnpm store + docker
- **节点能力不对等**。没有 docker 的节点只能承接 D1 里的轻量档（构建+lint），跑不了端到端复现。调度器需要**按能力路由**，而不只是按空闲数分配
- **双通道并发上限**。轻量档（构建/lint）和重量档（端到端全栈）资源画像完全不同，必须各自独立限流，不能共用一个数字
- **动态上限的计算依据**：按节点的内存余量 / 磁盘余量 / CPU 水位实时推导，而非静态配置一个常数。磁盘水位尤其关键（见 00-analysis 风险 1）
- **节点注册与健康检查**：节点上下线、任务超时后的重新派发、跨节点的任务状态一致性

**结论：D3 把项目从"一周可上线"推到"2~3 个月的产品"量级。** 这不是反对，是需要你明确接受的范围。

## 4. D2 的第二个后果：凭据体系

多租户意味着 Lathe 要代表**每个用户**去操作两个外部系统 + 一个模型入口：

| 需要什么 | 方案 |
|---|---|
| 读写 Linear issue / 回帖 / 改状态 | Linear OAuth（按用户授权，非全局 API key） |
| 拉代码 / 推分支 / 开 PR | **GitHub App**（按安装签发短期 token；不要收集用户的 personal PAT） |
| 调模型跑 agent | **走 CloudRouter** —— 每用户一个 token，成本核算/限额/审计已经是它的现成能力 |

最后一项是顺手的架构复用：Lathe 的模型消耗天然应该由 CloudRouter 计量，不必自己再造一套 token 统计和额度控制。

> **已知偏离（2026-08-13 记）**：上面这张表描述的是终态。实际落地的 P0/P1 收的
> 就是 personal token —— `integrations` 的 `linear` / `github` 两个 kind 存的正是
> PAT，设置页里也白纸黑字写着「Personal access tokens」。
>
> 这是明知故犯而非疏忽：只有一个用户时，GitHub App 的安装流程（建 App、配权限、
> 装到组织、处理 installation token 轮换）的成本远超收益。补偿措施是把 PAT 当作
> 真正的密钥对待 —— AES-256-GCM 加密入库、主密钥在库外、界面只回显掩码、可随时删除。
>
> 代价记在这里：P2 换 GitHub App / OAuth 时需要一次凭据迁移，且第二步做「每用户
> 绑自己的账号」会把偏离放大（从一个 PAT 变成 N 个）。把已接受的风险写下来，
> 比留一条谁都知道没在遵守的原则有用。

## 5. 修订后的分期路线

### Phase 0 — 闭环验证（单机、单用户、串行）
目标：证明「Linear 单 → 分诊 → 实现 → 分级验证 → PR → 回帖」这条链路真的能自动跑通一次。
- 修复 Linear MCP 端点（`/sse` → `/mcp`，当前 404）
- 回收 503 个已合入的 worktree，pnpm store 共享（解磁盘 98% 的燃眉之急）
- 任务状态机 + 持久化（可续跑、webhook 幂等）
- 分诊 agent + Plan-first 回帖 + 静默观察期
- 轻量档验证（构建+lint）先通，端到端档暂时跳过
- 失败三件套：回帖 / 保留现场 / 推送通知
- **刻意不做**：多用户、多节点、并发、Web UI

### Phase 1 — 验证基建（本产品的真正价值）
- per-task compose project：动态端口 + 独立 DB schema + 全栈隔离
- 端到端档：复现原 bug → 应用改动 → 证明修复 → 回归检查
- D1 的任务类型分级路由器
- 单机受控并发（双通道限流）

### Phase 2 — 产品化（多租户）
- Linear OAuth + GitHub App + CloudRouter token 绑定
- 按用户的额度与并发配额

## 5.1 D5：先做本地账号体系，OAuth 绑定仍留在 P2（2026-08-13）

**决策**：平台登录用本地邮箱 + 口令（bcrypt），不等 OAuth。

**为什么不直接上 OAuth**：原路线把「谁能登录 Lathe」和「Lathe 拿什么身份去操作
Linear/GitHub」绑成了一件事，于是登录功能被 OAuth 的工期挡住。可这两件事是正交的
—— 一个只想看看任务看板的人，不该先去装一个 GitHub App。

**范围（第一步，已交付）**：
- 开放注册（邮箱 + 口令，无需邮箱验证）、登录、登出、改密
- 忘记密码走 SMTP，配置在设置页，保存时真投一封测试邮件验证
- 两级角色：管理员 / 普通用户；管理员另有用户管理页（列表 + 每人任务计数、
  启用停用、代重置密码、删除用户及其数据）
- 内置超管由启动逻辑播种，初始口令只打印一次并强制首登改密
- 会话落库（`sessions` 表），停用与代重置能立刻掐断在线会话

**刻意不做（留给第二步）**：数据仍然共享 —— 任务、仓库配置、Linear/GitHub 凭据
都挂在内置管理员名下，任何登录用户看到的是同一份。按 `owner_id` 全链路隔离与
每用户专属 webhook 回调地址是下一步。

**代价**：开放注册意味着「重复邮箱必然返回 409」，注册接口天然可用来枚举已注册
邮箱。这与「不泄露账号是否存在」有固有矛盾，选了开放注册就得接受。补偿是把这条
妥协限制在注册接口内：忘记密码接口对存在与不存在的邮箱返回逐字节相同的响应，
且把查库发信全丢进后台协程，连耗时都不泄露。

### Phase 3 — 横向扩展（多节点）
- 节点注册 + 健康检查 + 能力声明
- 按能力路由的调度器 + 动态并发水位
- 跨节点仓库缓存与依赖 store
