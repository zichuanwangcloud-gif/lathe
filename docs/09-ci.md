# 09 · CI 门禁与发布流水线

跑在 GitHub 托管 runner 上，两条流水线：`.github/workflows/ci.yml` 是门禁，
`.github/workflows/release.yml` 是发布。发布会先复用门禁，不给 tag 开后门。

## 1. 为什么第一件事是堵住「伪绿」

接 CI 之前实测过一次：把 `LATHE_TEST_DSN` 指向一个连不通的地址，跑五个核心包 ——

```
ok  internal/httpapi  0.044s     ← 带库时是 17.001s
ok  internal/task     0.016s
ok  internal/store    0.020s
ok  internal/flow     0.012s
ok  cmd/lathe         0.013s
```

全绿，0.1 秒跑完。原因是各测试包的 DB helper 都写了「连不上就 `t.Skipf`」。
这个行为对本地开发是对的（没起基础设施也能跑纯逻辑测试），但直接搬进 CI 就成了
陷阱：**Postgres service 起晚一秒、DSN 写错一个字符，流水线照样全绿，而它什么都
没验证。**

所以先有了 `internal/testsupport`：把「跳过还是失败」收成一个开关。

| 环境 | `LATHE_TEST_REQUIRE_DB` | 连不上库时 |
|---|---|---|
| 本地 `make test` | 不设 | `t.Skip`，体验不变 |
| 本地 `make test-ci` | `1` | `t.Fatal` |
| CI test job | `1` | `t.Fatal` |

原先散在 6 个文件里的 7 个 helper（`task` / `flow`×3 / `store` / `httpapi` /
`runner` / `cmd/lathe`）统一走这个包，DSN 默认值也只剩一处。

## 2. 门禁（ci.yml）

PR 与 push main 触发，三个 job 并行。PR 上新 push 会取消旧运行，main 上不取消。

### lint

`gofmt -l` → `go vet ./...` → `golangci-lint`。范围用 `git ls-files "*.go"` 圈定，
与 `make lint` 一致 —— 避开 `.claude/` 下的 worktree 检出副本。

golangci-lint 是**宽松起步**：`.golangci.yml` 里设了 `new-from-rev: origin/main`，
只对相对 main 的新增改动报错。存量代码从没跑过 errcheck / staticcheck，一次性全量
强制只会把 CI 卡在红灯上。等存量降到可控量再考虑去掉这行收紧。

### test

Postgres 16 service，端口**刻意映射成 55432**，与 `docker-compose.dev.yml` 对齐 ——
这样 `LATHE_DB_PORT` 和 `LATHE_TEST_DSN` 的代码默认值在 CI 里同样成立，少一处
「本地能跑、CI 配漏了」的漂移面。

步骤：编译二进制 → `migrate up` → **回滚再前滚** → 跑测试 → 汇总跳过项。

回滚校验这步值得说明：`migrate down` 是**单步**语义（实测只退最高版本，不是清空），
所以做的是 `up` → `down` 一步 → `up` 一步，挡住「新迁移忘了写 down / down 脚本
写错」。20 个 `.down.sql` 在此之前从没被任何流程验证过。

`LATHE_DB_*` 刻意只加在跑 migrate 的那两步上，不放 job 级：`internal/config`
的 `TestLoadDefaults` 断言的是「没有环境变量时的默认值」，job 级导出这些变量等于
把测试的前提改掉了。搭这套流水线时用 55434 的临时库验证，就是这么炸出来的 ——
CI 里因为端口恰好也配成 55432 而碰巧能过，属于脆弱的巧合，不能依赖。

测试固定 `-p 1`。这是硬约束：领单调度器 `task.Machine.ClaimReady` 是全局查询、
不按包隔离，多个测试包并行跑在同一个库上会互相抢 `queued` 行。

最后一步把**跳过的测试列进 job summary**，不阻塞。跳过的主要是 `internal/preview`
的 docker 集成测试（「镜像未缓存就跳过，测试不拉取」）—— 托管 runner 上没有预热
镜像，这部分跑不了。列出来是为了不让绿灯被误读成「全都验过了」；数据库测试已由
`LATHE_TEST_REQUIRE_DB` 强制，不会出现在这张表里。

> **已知缺口**：preview 的容器编排逻辑目前只有本地能验。改动那一块时请在本地跑
> 完整测试，别只看 CI 绿灯。后续要补的话，方向是加一个夜间 job 预拉镜像再跑。

### build

直接走完整 `Dockerfile`（`push: false`），而不是分别跑 pnpm build + go build。
理由是「前端产物覆盖 `internal/webui/dist` 再 `go:embed`」这个顺序容易写错，
Dockerfile 里已经处理好了，CI 再实现一遍就是第二份会腐烂的真相。

## 3. 发布（release.yml）

`v*` tag 触发，`validate → gate → (image, binaries) → release`。

**validate**：tag 必须是合法语义化版本；正式版必须在 `CHANGELOG.md` 里有对应的
`## [x.y.z]` 段落，否则直接失败。v0.1.1 就是发了 tag 却没写日志，这一步专门挡这个。
预发布（`v0.2.0-rc1`）跳过 CHANGELOG 校验。

**gate**：`uses: ./.github/workflows/ci.yml`，发布前过同一套门禁。

**image**：`linux/amd64,linux/arm64` 推到 `ghcr.io/<repo>`。为此改了 Dockerfile：
阶段 1、2 加 `--platform=$BUILDPLATFORM`，Go 编译改成 `GOOS/GOARCH` 交叉。
`CGO_ENABLED=0` 本就不需要目标平台的 C 工具链，交叉编译没有代价，而让 buildx 用
QEMU 模拟 arm64 跑 golang 镜像的话，光 Go 编译就要十几分钟。阶段 3 的运行时镜像
仍是真正的目标架构，`apk add` 那几条要靠 QEMU 模拟 —— 只装几个包，开销可接受，
所以 workflow 里保留了 `setup-qemu-action`。

镜像 tag 由 `metadata-action` 生成（`{{version}}` 与 `{{major}}.{{minor}}`），
`latest=auto` 保证预发布不会覆盖 `latest`。

**binaries**：`linux/amd64`、`linux/arm64`、`darwin/arm64` 三个交叉编译产物 +
`checksums.txt`。这条路径自己构建一份前端（镜像那条走的是 Dockerfile），因为
二进制要内嵌 UI。

**release**：从 CHANGELOG 摘出本版本段落作为 release notes，创建**草稿**。
产物和说明都备好，留一次人工过目再点发布。

## 4. 本地怎么对齐

```bash
make lint      # 与 CI 的 lint job 同口径（golangci-lint 需另装）
make test-ci   # 与 CI 的 test job 同口径：库连不上直接失败
```

CI 的判定基线：827 个测试通过、0 跳过（在镜像齐全的机器上），全量约 2 分 15 秒。
